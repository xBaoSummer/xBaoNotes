# xBaoNotes 执行与质量标准 v1.0

## 1. 开发节奏

每次只推进一个小目标。优先完成可验证的基础能力，再进入复杂功能。

推荐顺序：

1. 文档确认。
2. 项目骨架。
3. 数据保存。
4. 主页面管理。
5. 回收站。
6. 富文本和附件。
7. 桌面贴出。
8. 贴边入口。
9. 提醒。
10. 密码锁、备份、打包。

## 2. 每次开发前

必须检查：

- `docs/requirements.md`
- `docs/development-plan.md`
- `dev-logs/todo.md`

如果需求不清楚，先整理文档或向用户确认，不直接猜测大功能。

## 3. 每次开发后

必须更新：

- `dev-logs/progress.md`
- `dev-logs/todo.md`

`progress.md` 记录：

- 日期
- 完成事项
- 修改文件
- 验证结果
- 遗留风险

`todo.md` 记录：

- 当前阶段
- 下一步任务
- 待确认问题
- 暂缓事项

## 4. 数据安全

涉及用户数据的功能必须遵守：

- 删除先进入回收站。
- 彻底删除必须确认。
- 恢复备份前必须保留当前数据。
- 附件不能只保存原始路径，必须复制到软件管理目录。
- 数据库结构变更必须考虑迁移。

## 5. UI 质量

界面提交前必须检查：

- 日间模式可读。
- 黑夜模式可读。
- 文字不重叠。
- 按钮尺寸可点击。
- 主要操作路径清楚。
- 贴边入口不遮挡正常工作区域。

## 6. 功能验收

每个阶段至少做一次手动验证：

- 应用可启动。
- 新增数据可保存。
- 重启后数据存在。
- 删除后可恢复。
- 设置项保存后重启仍生效。

Phase 10 之后的正式发布前，必须参考 `docs/test-checklist.md` 做发布前抽查，并在 `dev-logs/progress.md` 记录执行情况。

## 7. 日志记录标准

开发日志使用 Markdown。每次记录保持简洁，但必须能让下一次开发快速接上。

示例：

```markdown
## 2026-06-12

### Completed
- 建立项目文档和开发日志。

### Changed Files
- AGENTS.md
- docs/requirements.md

### Verification
- 已确认文件创建成功。

### Risks
- 暂无。
```

## 8. 用户沟通

用户不懂代码，回复时应避免堆叠技术细节。需要说明：

- 做了什么。
- 为什么这样分阶段。
- 当前是否可运行。
- 下一步建议做什么。
